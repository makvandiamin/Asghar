# Part II: Research and Development of a New Method for Training and Storing Ultra-Compact Weights

## Research Goal

Investigate and experimentally develop a method in which the model learns from the training stage using a highly compressed weight representation, rather than merely quantizing or compressing a ready-made model after training. The long-term goal is to dramatically reduce model-weight size while preserving as much quality as possible. Ratios such as 10:1 are experimental targets, not guarantees.

## Initial Hypothesis

Investigate the following hybrid method as a hypothesis, not an established fact:

1. Low-bit or ternary representation for some weights.
2. Learnable codebooks or group coding to represent weights using shared codes.
3. Adaptive bit allocation based on layer sensitivity and validation quality.
4. Low-rank correction or higher-precision components only for layers shown by experiments to need them.
5. Lower-memory parameter training and updates, without assuming optimizer state can be removed at no cost.
6. A versioned binary weight format for weights, scales, codebooks, metadata, checksums, and all information required to reconstruct and run the model.
7. An inference engine that computes directly on the compressed representation when possible, rather than expanding all weights into a larger format at once.

## Mandatory Comparisons

Compare at least these baselines fairly and scientifically:

- A reference model at ordinary precision.
- Standard existing quantization.
- Training-aware low-bit/ternary methods.
- Codebook/vector-quantization methods.
- The proposed hybrid method.
- Sparsification or low-rank approximation methods, if feasible.

Use the same model and data, training budgets, and evaluation criteria for each method. If a baseline cannot be run, record why; never claim a comparison was performed when it was not.

## Evaluation Criteria

For every experiment, record:

- Parameter count and effective bits per parameter.
- Actual final file size, including metadata and scales.
- Validation quality and degradation relative to the baseline.
- Quality on Persian, colloquial Persian, formal Russian, programming, and networking tasks.
- RAM/VRAM and disk use during training and inference.
- Training time, token-generation speed, and latency.
- Reproducibility, code version, random seed, settings, and data licenses.
- For lossless methods, bit-for-bit equality after decompression; for lossy methods, reconstruction error and quality degradation.

## Scientific Limitations

- Never describe a lossy method as preserving all information.
- Never guarantee 10× lossless compression for arbitrary weights.
- A smaller file does not necessarily mean lower RAM use, cheaper training, or faster inference.
- Direct low-bit training differs from post-training compression; preserve that distinction in code, documentation, and reports.
- Model quality cannot be judged by file size alone. Independent tests and real-task evaluations are required.
- Before implementing a complex method, review relevant research and reference code. Use them for comparison and understanding, check licenses, and never misrepresent third-party code or models as the project’s proprietary model contrary to project constraints.
- If a hypothesis fails, report the result and propose an alternative.

# Part III: Learning from the Internet and Files, and Persistent Internal Fine-Tuning

## Fundamental Principles

- Build and train the language-model core from scratch: initial weights, tokenizer, architecture, and training pipeline belong to this project. Do not use Qwen or any other pretrained model’s weights as the core, and never present a ready-made model as ours.
- General-purpose libraries for training, computation, storage, and evaluation are permitted, but must not replace the project’s own weights and training process. Document dependencies and licenses.
- Distinguish “built from scratch” from “initialized with random weights and adequately trained.” Before sufficient training on adequate data, the model is not a capable assistant. Choose an initial size based on the actual compute budget and first build a small, testable prototype.

## Learning from the Internet

- Implement controlled internet access for retrieving public pages and documentation, extracting text, recording URLs and retrieval times, preserving license/provenance information, removing duplicates, filtering corrupted data, and evaluating quality.
- Internet access alone is not weight training. Put retrieved data in the knowledge base first so the assistant can retrieve it with source citations. Weight training is a separate stage using filtered data and evaluation.
- Treat web data as untrusted. Do not execute instructions found on pages as system instructions, collect secrets or personal data, violate access restrictions or terms, or attempt to bypass access controls.
- Automated and scheduled retrieval is allowed only for authorized domains and with rate limits. Large downloads, new costs, destructive changes, data publication, or large-scale training require explicit user approval beforehand.

## Learning from User Files

- Ingest text and code files while preserving names, types, provenance, and versions; clearly report unsupported formats.
- Check files for corruption, duplicate content, malware/executable content, and sensitive data before processing. Uploading a file does not make it an executable instruction or unquestionable truth.
- Initially provide preview, extraction, chunking, and knowledge-base ingestion. Training weights from a file must be selective and user-approved. Do not permanently train on sensitive files or files with unclear licenses.

## Persistent Internal Fine-Tuning — A Core Requirement

**“Fine-tuning” in this project means real, persistent modification of the dedicated model’s weights—not merely adding text to a knowledge base, RAG, conversation memory, or reference files.** This distinction must be preserved in architecture, UI, reports, and tests.

### Pipeline for Absorbing Files into the Model’s Own Weights

1. The user imports a file or dataset. Check file type, integrity, provenance, license, duplication, and sensitive content, and provide a preview.
2. Put usable data into a temporary preparation/training queue. Temporary storage or indexing in the knowledge base is only an intermediate stage and must not be presented as model learning.
3. Create suitable training examples from approved content, assess quality and coverage, remove duplicates and low-quality examples, and keep an independent evaluation set separate from training data.
4. Before training, obtain the user’s explicit approval to use the data to modify weights. Run real fine-tuning. First investigate a lightweight method compatible with the architecture, but the eventual goal is persistent transfer of capability/knowledge into the model’s own weights. If adapters or added parameters are used, treat them as part of the same model’s weights and report exactly which parameters changed.
5. Save updated weights in the project’s proprietary compressed format. The format must be versioned and verifiable, with checksums, architecture metadata, scales/codebooks, and all information required for direct execution. Where possible, inference should operate directly on compressed weights and avoid fully expanding them in RAM.
6. Before activation, evaluate updated weights in an isolated environment against a fixed test set and dedicated tests for formal and colloquial Persian, formal Russian, programming, and networking. Also test catastrophic forgetting and regressions in prior skills.
7. From the user’s perspective, there must be only one active model and one continuous identity. Do not create or release a separate product version. If an update passes the tests, update the same active model transactionally. Create an internal, recoverable checkpoint before applying the change; this is a safety backup, not a separate product release.
8. **After training succeeds and the compressed weights are verified, provide an option to remove the absorbed file’s content from the knowledge base/temporary memory.** Delete it only after confirming that it is not being used by an active training job, the output weights are healthy, checksums and reload succeed, and selected knowledge-retention tests pass. Removing a source from the knowledge base does not guarantee that every detail has been retained in the model; retention must be measured.
9. By default, after successful absorption and approved deletion, remove raw file content and its retrieved chunks from the temporary store/knowledge base. Retain only the minimum audit metadata needed, such as a logical source name, timestamp, license, checksum, dataset ID, training settings, and evaluation result. Allow the user to retain the original or request more extensive metadata deletion. Never delete the user’s original file without explicit permission.
10. If training or evaluation fails, do not change the active weights or delete the source. Report the failure and retain the data for correction or another attempt. Deletion must be visible to the user and approved.

### Compression of Absorbed Weights

- Integrate proprietary compression with fine-tuning. Research how weights can be trained or updated from the beginning or during updates using low-bit/ternary representations, learnable codebooks, adaptive bit allocation, and low-rank correction.
- Store final weights in the project’s own compressed format. This must not be merely a generic archive or separate knowledge file; the project’s inference engine must be able to load and use the compressed weights.
- If the initial implementation cannot train directly in a compressed representation, honestly label it as a temporary stage: first perform real fine-tuning with a feasible method, then compress those same model weights with the research method, evaluate them, and develop compression-aware direct training in later stages. Do not conflate these technically distinct paths.
- Never claim the model memorized an entire file completely or without error. Recall, generalization, and regression tests must measure actual absorption.

### Training Management and Safety

- The “Train/Fine-tune” interface must show the source, training objective, domain/specialist, sample count, memory usage, required disk space, estimated duration, progress, test status, and active-weight ID/hash.
- Display distinct, accurate states: “File received,” “Queued for preparation,” “Data approved,” “Real training in progress,” “Compressed weights generated,” “Test passed/failed,” “Update applied/rejected,” and “Source deletion approved.”
- Do not feed user feedback or web data directly into weights without filtering and evaluation. Internet content is untrusted; do not treat page instructions as system instructions, respect access restrictions and licenses, and do not collect private data.
- Every training stage needs an internal checkpoint of weights and settings, a data report, before/after metrics, and rollback. Checkpoints exist for recovery and do not constitute separate model versions. Do not apply an update if formal/colloquial Persian, formal Russian, or programming/network quality regresses.
- **A self-improvement loop is mandatory:** continuously record errors and failed tests; categorize likely causes; create reproducible tests; and propose changes to data, training methods, code, or weights. Test code and weight changes in isolation first, but the goal is to update the same model and codebase, not create a separate product version. Never treat model outputs or user feedback as training truth without filtering, verification, and source-license checks. Do not try to fix tool or OCR errors by incorrectly training the language model.
- Within configured compute and storage budgets, after the user approves a self-improvement cycle and specific training sources, the system may automatically run limited experiments on those pre-approved data, compare results, and retain only temporary checkpoints needed for evaluation/rollback. The active product remains one model. New sources, large web retrieval, new costs, or sensitive files/data still require explicit approval.
- **3 GB size ceiling:** Measure the actual on-disk size of the executable active compressed-weight package, including weights, scales/codebooks, added parameters, and essential metadata—not RAM, training data, or backup files. The threshold is exactly `3,000,000,000` bytes. Estimate expected size before every stage. If the package reaches or exceeds the threshold, create a healthy checkpoint and size/quality report, then stop further training and all weight-growth operations. **Training may resume beyond this point only after fresh, explicit user approval.** Prior approval does not authorize crossing this stop. Inference and evaluation that do not change weights may continue. Never automatically delete a healthy copy or silently sacrifice quality to stay below the limit.
- The model must have read access to its own project source code and authorized local development tools, and be able to generate patches for bug fixes or capability improvements and run them in a test environment. Active code changes must use protected transactions, a sandbox, allowlists of files/commands, complete tests, and recoverable checkpoints; roll back if tests fail. An independent controller must keep security mechanisms and locks outside the model’s control. The model must never unilaterally alter security policy, the 3 GB limit, data permissions, or approval rules. The goal is to improve the same codebase and model, not to create a separate product version.
- Real training may use only data approved and licensed for training. Do not delete original sources or perform destructive operations without specific approval. Updates to the model’s own code and weights must follow the update policy and required tests. At the end of every cycle, report package size, active-weight hash, time and resources consumed, before/after results, possible regressions, and the reason for applying or rejecting the change.

## Mandatory Operational Method for Safely Updating the Same Model

These are operational rules for self-improvement. If they conflict with more general descriptions, these rules take precedence.

### 1. One Active Model; No New Product Release

- Show only one active model ID and one continuous identity in the product UI and logic. Temporary candidate weights in an isolated environment are allowed and necessary for testing; they are not separate product models or independently releasable versions.
- Update weights transactionally: write to a temporary file, verify completeness and checksum, test loading, run acceptance tests, and only then atomically swap the active-weight pointer/path. Never overwrite the active-weight file in place or leave it half-written.
- If the OS or filesystem cannot guarantee atomic replacement, use a manifest and active pointer that survive power loss. On startup, restore the latest complete, valid state.
- Do not alter weights currently being used for inference. Train in a separate process/environment; swap only after the candidate has loaded and passed tests. On low-memory devices, a controlled inference pause during replacement is preferable to excessive concurrent RAM use.

### 2. Model Access to Its Own Code Without Unrestricted Access

- Grant access only to the repository and explicitly approved project folders. Canonicalize paths and block access outside the project root, including keys, passwords, personal data, and system settings.
- The model may read code, create diffs/patches, and run tests. Commands must be executed only through the local coordinator, using an allowlist, time/RAM/disk limits, a sandbox, and complete event logging. Never directly execute generated text as shell commands or as code with unrestricted privileges.
- Changes to protected areas—security policy, permission controls, the 3 GB lock, approval system, backup/recovery logic, command allowlists, and access restrictions—must be blocked by guard code outside the model’s control. Do not rely solely on asking the model to obey these rules.
- Apply code changes in a temporary branch or working directory. Run formatters, static analysis, unit tests, integration tests, security tests, and rollback tests. Only a patch limited to permitted files and passing tests may be promoted to active code. If the project lacks sufficient tests, build baseline tests first and keep automatic promotion disabled until they pass.
- If a code fix requires changing weight structure, binary format, data migration, adding a dependency, or granting new access, stop and request explicit user approval; these are not routine automatic changes.

### 3. Train the Same Model’s Weights Without Damaging It

- Before training, record the state needed for recovery: active weights, manifest, model settings, training-code version, random seed, dataset ID/hash, and optimizer/scheduler state if needed. If optimizer recovery is unnecessary or too costly, document that limitation.
- Start candidate weights from a valid checkpoint and train in temporary storage. For low-memory systems, select batch size, sequence length, gradient accumulation, and checkpointing according to available resources. Estimate disk and RAM requirements before starting; do not begin if resources are insufficient.
- Before training, record baseline metrics on a fixed test set separate from training data. After training, rerun the same tests and regression tests. Acceptance must use pre-defined numeric thresholds: improvement on the target, no excessive degradation in previous languages/skills, no loading errors, compliance with the size ceiling, and reproducibility.
- Prevent test leakage: evaluation data must not enter training, training-data generation, or direct sample selection. Model-generated data requires independent validation and provenance labels; model output alone is not a ground-truth reference.
- After passing, transactionally register candidate weights as the active weights of the same model. After failure, leave active weights unchanged and report the reason for rejection. Keep the backup checkpoint until health checks after replacement pass; clean it up only under the retention policy and never remove the last recovery path.
- If weight changes do not produce measurable improvement, results conflict, or acceptance thresholds were not defined in advance, do not apply the automatic update. Stop the experiment and report.

### 4. Persistent 3 GB Ceiling Lock

- An independent controller outside the model’s control must measure the actual size of every active-weight package component and estimate expected size before training. The threshold is `3,000,000,000` bytes; do not activate a candidate that exceeds it.
- Store the lock state in protected, persistent settings so it survives restart, cache clearing, and session changes. The model must not be able to modify the lock file or controller code.
- Once the active package reaches the threshold, stop training and every weight-growth operation. Evaluation and inference without weight changes may continue. Resumption requires fresh, specific user approval for that stage; the approval request must include current size, estimated growth, cost, and risk.
- Measure and report safety checkpoints, candidate weights, and temporary files separately. Never evade the ceiling by hiding components, using hard links, omitting compression details, or automatically deleting the last backup.

### 5. Recovery from Crashes and Power Loss

- For every code/weight transaction, record a journal with operation ID, time, before/after hashes, changed files, test results, and commit state. Intermediate states must be detectable after restart.
- On startup, verify the active code/weight manifest and checksums. If replacement was incomplete, a checksum is wrong, or loading fails, restore the last complete valid state. If no valid backup exists, stop automatic changes and request user intervention.
- Before deleting any temporary file, verify that it is neither the last valid backup nor an active file and that no training/inference operation depends on it. Never delete the user’s original files during this cleanup.

### 6. Reporting and Safe Mode

- Every cycle must produce machine-readable and human-readable reports covering the goal, sources and permissions, changed files, code/weight hashes, actual package size, time/RAM/disk consumed, before/after results, regressions, accept/reject decision, and rollback status.
- If tests, data permissions, checksums, available storage, or package size cannot be verified, enter safe mode: do not change the active state, do not delete source data, and report the error.
- Self-improvement does not guarantee increased intelligence. If consecutive cycles show no improvement or repeated regressions, stop automatic training and continue diagnosis/evaluation only until the cause is understood.
- First validate these mechanisms with small synthetic data and fault/power-loss tests. Do not enable automatic active-weight or active-code updates until transaction, rollback, ceiling-lock, and sandbox tests pass.

## Local Coordinator and Policy for Adding an Auxiliary Model

- The first release must not include an auxiliary language model. Implement the coordinator using deterministic code, a simple state machine/workflow, defined tool interfaces, event logging, and error handling.

- The primary model must express tool requests in structured form. The coordinator must validate schemas, permissions, file paths, parameters, and resource limits. Never blindly execute model output as a system instruction or shell command.
- Require explicit user approval for sensitive actions such as deleting/overwriting files, changing model weights, real training, sending data to the internet, or substantial resource use. Enforce least privilege, logging, and rollback.
- Only after a deterministic baseline and real test set exist may you evaluate a small classifier trained from scratch. Do not build it by default; first demonstrate that current rules have a real problem and that the small model solves it better.
- If an optional component is built, keep it in an independent, disableable module and run an A/B comparison. Retain it only if it improves overall accuracy and task quality without disproportionate increases in size, RAM, latency, energy, or maintenance; otherwise remove it.

Basic functionality, the primary model, file management, local tools, and save/restore must work without external services. Clearly identify and keep optional any feature that requires internet access.

# Part VII: Optional Connection to Other Device Applications, with User Approval

## Feature Configuration Key

Connection to other applications on the device must be optional and disabled by default. Proposed configuration:

```yaml
device_app_integration:
  enabled: false
  require_user_approval: true
  approved_apps: []
  approved_actions: []
  allow_background_access: false
  audit_log: true
```

This is a proposed configuration contract. Until it is implemented and tested in the application, do not claim that the capability is operational.

## Mandatory Connection Rules

1. **Explicit activation:** Unless the user enables this feature in settings, the model must not attempt to connect to or control other applications.
2. **App and permission approval:** On the first connection to each app, clearly show the app name, connection type, requested permissions, and actions the model could perform. Obtain explicit approval. Enabling the overall feature does not grant unrestricted access to every app.
3. **Risk-proportionate confirmation:** Before sensitive or consequential actions—such as sending messages or email, publishing content, deleting or changing files, making payments or purchases, changing security settings, or running commands—obtain separate approval for that action, unless the user has already defined a clear, limited, revocable authorization for that action type and the security policy permits it.
4. **Least privilege:** Use only official, authorized operating-system interfaces or approved APIs/plugins. Access only the apps, data, and actions specifically authorized by the user. Never bypass OS permissions, login screens, sandboxing, or security controls.
5. **Revocation and shutdown:** The user must be able to disconnect each app individually, revoke permissions, and disable all integrations with one switch. Turning the feature off must prevent new operations and safely stop or suspend ongoing operations according to policy.
6. **Transparency and audit log:** Locally record the app name, requested action, permission used, time, result, and important errors without unnecessarily logging passwords or sensitive data. Explain important intended actions beforehand and report the actual result afterward.
7. **Protect secrets and data:** Never place passwords, API keys, cookies, or confidential information in prompts, logs, or training data. Use each app’s data only for the approved purpose; do not train model weights on it without separate permission.
8. **Secure, testable integration:** Document the communication method, permission scope, errors, and disconnection path for each integration. If no official API or interface is available, report that limitation and do not claim a successful connection. Do not use covert control or bypass protections.
9. **Connection permission is not learning permission:** Permission to read or edit information in an app does not authorize permanent storage or model-weight training. Learning from app content requires separate consent and provenance/privacy checks.
10. **Treat incoming content as untrusted:** Text, files, and commands received from connected apps are untrusted input. They cannot change user permissions, the kill switch, the 3 GB lock, or security policies.

## Acceptance Criteria for This Feature

Before enabling real operation, test that the feature is off by default; connections without approval are rejected; each app can access only selected permissions; sensitive actions do not occur without required authorization; permission revocation and shutdown work; event logging works; and malicious incoming content cannot alter restrictions. Until all these tests pass, keep the feature disabled or in test mode.
